DARS 11 · MODUL D · JAMOA · YAKUNIY DARS

Professional odatlar: .gitignore, commit message, README

Kursning oxirgi darsi. Bu yerdagi uch narsa texnik jihatdan oson — lekin aynan ular «Git biladi» bilan «u bilan ishlash yoqimli» orasidagi farqni yaratadi.

📱 O'qish ≈ 9 daqiqa 💻 Amaliyot ≈ 15 daqiqa Kerak: Dars 10

Nega bu muhim

Shu paytgacha mexanikani o'rgandingiz — Git nima qilishini. Bugungi uch narsa esa hamkasblaringiz uchun: ular sizning repongizni ochganda, tarixingizni o'qiganda va loyihangizni birinchi marta ishga tushirganda his qiladigan narsa. Ishga qabul qilishda ham ko'pincha aynan shunga qaraladi.

1. .gitignore — Git nimani ko'rmasligi kerak

Har bir loyihada Git kuzatmasligi kerak bo'lgan fayllar bo'ladi. .gitignore — shularning ro'yxati.1

Nimalarni yozadi va nega

NimaNega
Sirlar
.env · parollar.txt · *.key		 🔴 Eng muhim sabab. Parol yoki API kaliti bir marta push qilinsa, u tarixda abadiy qoladi — faylni keyin o'chirsangiz ham eski commitdan topib olish mumkin. Ya'ni «keyin o'chiraman» ishlamaydi. Boshidan yozmaslik kerak.
Yaratiladigan fayllar
node_modules/ · build/ · __pycache__/		 Ular koddan qayta yaratiladi — saqlashning ma'nosi yo'q. Hajmi katta va har commitda minglab qator «o'zgarish» ko'rsatib, haqiqiy ishni ko'rinmas qiladi.
Shaxsiy fayllar
.idea/ · .vscode/ · .DS_Store		 Bu sizning muharriringiz sozlamalari. Hamkasbingizga keraksiz va uning sozlamalari bilan to'qnashadi.

Qanday yoziladi

Oddiy matn fayli, loyihaning ildizida (root). Har qator — bitta qoida:

.gitignore
# Sirlar — hech qachon GitHub'ga chiqmasin
.env
*.key.key bilan tugagan hamma fayl
# Yaratiladigan fayllar
node_modules// = butun papka
*.log
# Lekin bu bittasi kerak
!muhim.log! = istisno
  • # — izoh (Git e'tiborsiz qoldiradi);
  • * — istalgan matn: *.log = barcha .log fayllar;
  • / oxirida — papka: node_modules/;
  • ! — istisno: yuqorida rad etilgan narsani qaytarib qo'shadi.
Noldan yozmang

Deyarli har bir til va muhit uchun tayyor .gitignore bor: github.com/github/gitignore (Python, Node, Java…). Yangi loyiha ochganingizda GitHub ham buni taklif qiladi. Nusxa oling va o'zingiznikini qo'shing.

Sizda allaqachon bor

Kurs repongizda .gitignore bor va u ishlab turibdi: NOTES.md va learning-records/ — bu mening o'qituvchilik eslatmalarim, ular public saytga chiqmaydi. Shu sababli siz ularni GitHub'da ko'rmaysiz, kompyuteringizda esa turibdi.

⚠️ Eng ko'p uchraydigan chalkashlik

.gitignore allaqachon kuzatilayotgan faylga ta'sir qilmaydi

Agar faylni bir marta commit qilib bo'lgan bo'lsangiz, uni .gitignorega yozish hech narsa qilmaydi — Git uni kuzatishda davom etadi.

Yechim: avval kuzatuvdan chiqaring, keyin ignore ishlaydi:

git rm --cached fayl.log

--cached — faqat Git'dan chiqaradi, fayl diskingizda qolaveradi. (--cachedsiz yozsangiz, fayl o'chib ketadi — ehtiyot bo'ling.)

2. Commit message — tarix o'qiladigan hujjat

Bitta qoida hamma narsani tushuntiradi:

Asosiy qoida

Diff nima o'zgarganini ko'rsatadi. Izoh nega o'zgarganini aytishi kerak.2

Kodni o'qib «nima o'zgargani»ni har doim topa olasiz. «Nega» esa faqat sizning boshingizda — va uni yozmasangiz, olti oydan keyin o'zingiz ham eslay olmaysiz.

YomonYaxshi
fix Bo'sh email bilan ro'yxatdan o'tish xatosi tuzatildi
update Login sahifasiga parolni tiklash havolasi qo'shildi
asdf · o'zgarishlar Sekin ishlagan qidiruvga indeks qo'shildi

Uzunroq izoh kerak bo'lsa

Katta yoki g'ayrioddiy o'zgarishda ikki qismli izoh yozing: qisqa sarlavha, keyin tafsilot. Terminalda ikkita -m bilan:

git commit -m "Qidiruvga indeks qo'shildi" -m "Qidiruv 4 soniya davom etardi. Sabab: baza har so'rovda butun jadvalni o'qir edi."

Birinchi -m — sarlavha (git log --onelineda shu ko'rinadi), ikkinchisi — tavsif (git showda ochiladi).

Ba'zi jamoalarda old qo'shimcha ishlatiladi

feat: (yangi imkoniyat), fix: (tuzatish), docs: (hujjat). Masalan: fix: bo'sh email xatosi. Bu «Conventional Commits» deb ataladi. Majburiy emas — ish joyingizdagi odatga qarang va o'shanga moslashing.

3. README.md — loyihaning yuzi

GitHub repo sahifasini ochganda, fayllar ro'yxati ostida README.md avtomatik ko'rsatiladi.3 Ya'ni bu — loyihangizning birinchi taassuroti. Odam sizning kodingizni o'qishdan oldin shuni o'qiydi.

Yaxshi README uch savolga javob beradi:

  1. Bu nima? — bir-ikki jumlada, oddiy tilda.
  2. Qanday ishga tushiraman? — aniq qadamlar, ko'chirib qo'yish mumkin bo'lgan buyruqlar.
  3. Qanday hissa qo'shaman? — jamoa loyihasi bo'lsa.

.md — Markdown: oddiy matn, bir nechta belgi bilan bezatiladigan. Kerakli qismi juda kichik:

Amaliyot: uchalasini ham qo'llaymiz

Bugungi mashq haqiqiy foyda beradi: kurs repongizga README yozasiz — u GitHub'da hamma ko'radigan sahifa bo'ladi.

Va butun ishni 10-darsdagi kundalik ritm bo'yicha qilamiz — ya'ni bu ayni paytda yakuniy takrorlash ham.

A qism — .gitignore

  1. Ritm bo'yicha boshlang

    Kun boshi + ish uchun branch.

    cd ~/Projects/Learn/Git && git switch main && git pull && git switch -c professional-odatlar

    Kutilgan natija: «Switched to a new branch 'professional-odatlar'».

  2. «Sir» fayl yarating va Git uni ko'rayotganini tekshiring

    Bu haqiqiy parol emas — mashq uchun.

    echo "PAROL=123456" > .env && git status --short ?? .env

    Kutilgan natija: ?? .env — Git uni ko'ryapti va commit qilishga tayyor. Xavfli holat.

  3. .gitignorega qo'shing

    >> — mavjud faylning oxiriga qo'shadi (ichidagini o'chirmaydi).

    printf "\n# Sirlar\n.env\n*.log\n" >> .gitignore && git status --short M .gitignore

    Kutilgan natija: .env ro'yxatdan yo'qoldi! Faqat .gitignorening o'zgargani ko'rinadi. 1-g'alaba. 🎉

  4. 🪤 Endi tuzoqni ko'ring: avval commit qilingan fayl

    Ataylab «xato» qilamiz — faylni ignore qilishdan oldin commit qilamiz.

    echo "test log" > vaqtinchalik.log && git add -f vaqtinchalik.log && git commit -m "Vaqtinchalik log fayli (ataylab)"

    Kutilgan natija: commit yaratildi. -f = «ignore qilinganini bilaman, baribir qo'sh».

  5. Fayl hali ham kuzatilayotganini tasdiqlang

    *.log qoidasi .gitignoreda bor — lekin fayl allaqachon kuzatuvda.

    echo "yana qator" >> vaqtinchalik.log && git status --short M .gitignore M vaqtinchalik.log

    Kutilgan natija: M vaqtinchalik.log — Git uni hamon kuzatyapti. Mana o'sha chalkashlik.

  6. Kuzatuvdan chiqaring

    --cached — faqat Git'dan chiqaradi, fayl diskda qoladi.

    git rm --cached vaqtinchalik.log && git status --short rm 'vaqtinchalik.log' M .gitignore D vaqtinchalik.log

    Kutilgan natija: ls deng — fayl diskda joyida, lekin Git endi uni kuzatmaydi. 2-g'alaba. 🎉

B qism — README yozamiz

  1. Mavjud README'ga o'z bo'limingizni qo'shing

    Repongizda README allaqachon bor — men yozib qo'yganman. Haqiqiy ishda ham ko'pincha shunday bo'ladi: noldan yozmaysiz, mavjudini to'ldirasiz. >> (ikkita) — oxiriga qo'shadi, ichidagini o'chirmaydi. Copy tugmasidan foydalaning.

    cat >> README.md << 'EOF' ## Mening natijalarim (bir necha qator — Copy tugmasida to'liq) EOF

    Kutilgan natija: jimlik. tail -8 README.md deng — yangi bo'lim faylning oxirida paydo bo'ldi, eskisi joyida.
    Agar terminal > belgisi bilan kutib qolsa: oxirgi EOF qatori tushmagan. EOF deb yozib Enter bosing.

  2. Matn muharririda o'zingizga moslang (ixtiyoriy, lekin tavsiya qilaman)

    Uzun matnni terminalga emas, muharrirga yozgan qulay. VS Code'da: code README.md, yoki fayl menejeridan oching.

    Qo'shgan bo'limingizni o'zgartiring — Markdown belgilarini yuqoridagi jadvaldan qarang. Masalan:

    README.md — o'z bo'limingiz
    ## Mening natijalarim
    Kursni **2026-yil avgustda** boshladim.
    - Eng qiyin bo'lgani: `merge conflict`
    - Eng foydali bo'lgani: `git reflog`
    - Keyingi maqsad: real loyihaga birinchi PR

    Bu — sizning repongiz. README'da o'z ovozingiz bo'lgani yaxshi.

  3. Yaxshi izoh bilan commit qiling

    Ikkita -m: sarlavha + tavsif. Sarlavha nima, tavsif nega.

    git add -A && git commit -m "README va .gitignore qo'shildi" -m "README repo sahifasida kursning nimaligini tushuntiradi. .gitignore esa sirlar (.env) va log fayllar tarixga tushmasligi uchun."

    Kutilgan natija: commit yaratildi. git show --stat deng — sarlavha va tavsif alohida ko'rinadi.

C qism — ritmni yakunlang

  1. Push qiling va PR oching

    10-darsdagi tartib — endi mustaqil bajarasiz.

    git push -u origin professional-odatlar

    Bajaring: GitHub'da Compare & pull request → Create pull request → Merge pull request → Delete branch.

  2. Aylanani yoping va natijani ko'ring

    git switch main && git pull && git branch -d professional-odatlar

    Kutilgan natija: README endi mainda. GitHub'da repongizni oching — README sahifada chiroyli ko'rinadi. 3-g'alaba! 🎉🎉

Tozalash (ixtiyoriy)

Mashq fayllari (.env, vaqtinchalik.log, ritm.txt, hamkasb.txt…) kerak bo'lmasa, keyingi safar birga tozalaymiz — ayting. .env va *.log allaqachon ignore qilingan, shuning uchun ular GitHub'ga chiqmaydi.

Yodda tuting (checklist)

💻 Amaliy qism kompyuterda

Amaliyotda soxta .env fayli yaratib, uni .gitignore bilan yashirasiz; keyin tuzoqni ko'rasiz — avval commit qilingan fayl ignore qilinmaydi va uni git rm --cached bilan chiqarasiz. So'ng repongizga haqiqiy README yozasiz, ikki qismli izoh bilan commit qilasiz va butun ishni 10-darsdagi ritm bo'yicha PR orqali qo'shasiz. 10 qadam.

Tekshirib ko'ramiz (quiz)

SAVOL 1 Parolni commit qilib, push qildingiz. Keyin faylni o'chirdingiz. Xavfsizmi?

To'g'ri, va bu jiddiy xavf. Tarix — hamma commitlar. Shuning uchun sirlarni boshidan .gitignorega yozing. Agar tushib qolsa — parolni almashtiring.

SAVOL 2 Faylni commit qilib bo'lgansiz. Endi .gitignorega yozdingiz. Nima bo'ladi?

To'g'ri — .gitignore faqat hali kuzatilmagan fayllarga ta'sir qiladi. Yechim: git rm --cached fayl.

SAVOL 3 Commit izohi nimani aytishi kerak?

To'g'ri. «Nima» kodda ko'rinadi, «kim va qachon» Git o'zi yozadi. Faqat «nega» sizning boshingizda — uni yozib qo'ymasangiz, yo'qoladi.

SAVOL 4 git rm --cached fayl.log nima qiladi?

To'g'ri. --cached = «faqat Git'dan». Usiz yozsangiz, fayl o'chib ketadi — shuning uchun diqqat bilan yozing.

Eslab ayting (o'zingizni sinang)

Bu — kursning oxirgi eslab-aytish to'plami. Oxirgi uchtasi butun kursni qamrab oladi.

.gitignorega birinchi navbatda nima yoziladi?

Sirlar — .env, parollar, API kalitlari. Chunki bir marta push qilinsa, ular tarixda abadiy qoladi.

.gitignore qachon ishlamaydi?

Fayl allaqachon commit qilingan bo'lsa. Yechim: git rm --cached fayl — kuzatuvdan chiqadi, disk'da qoladi.

Commit izohining oltin qoidasi?

Diff nima o'zgarganini ko'rsatadi — izoh nega o'zgarganini aytishi kerak.

README uch savolga javob beradi — qaysilar?

1) Bu nima? · 2) Qanday ishga tushiraman? · 3) Qanday hissa qo'shaman?

↩︎ Kurs bo'yicha: kundalik aylananing besh qadami?

pull → branch → ishla+commit → push → PR/merge → yana pull. (Dars 10)

↩︎ Kurs bo'yicha: konflikt belgilari va hal qilish qadamlari?

<<<<<<< HEAD sizdagi · ======= chegara · >>>>>>> kelayotgan. Hal qilish: tahrirla (belgilarni o'chir) → git add → git commit. (Dars 08)

↩︎ Kurs bo'yicha: Git'ning oltin qoidasi?

Commit qilingan narsani yo'qotish juda qiyin, commit qilinmaganini esa oson. Shuning uchun tez-tez commit qiling. (Dars 03)

Cho'ntak xulosasi
  • .gitignore: sirlar · yaratiladigan fayllar · shaxsiy fayllar. # izoh · * namuna · / papka · ! istisno.
  • ⚠️ Allaqachon commit qilingan faylga ta'sir qilmaydi → git rm --cached fayl.
  • Sir push qilinsa — tarixda qoladi. Faylni o'chirish yetarli emas, parolni almashtiring.
  • Commit izohi: diff nimani ko'rsatadi — izoh negani aytadi. Ikki qismli: git commit -m "sarlavha" -m "tavsif".
  • README: bu nima · qanday ishga tushiraman · qanday hissa qo'shaman.

Siz endi jamoada Git bilan ishonch bilan ishlay olasiz. Bu kursni boshlaganingizda Git tajribangiz nolga teng edi — bugun sizda 11 dars, o'nlab commit, haqiqiy pull request va o'z qo'lingiz bilan hal qilingan merge conflict bor.

Endi eng muhim qadam: haqiqiy amaliyot

Kurs — bu mashq maydoni. Haqiqiy mahorat real muhitda shakllanadi. Uch taklif, oson tartibda:

  1. GitHub Skills — skills.github.com. GitHub'ning o'zida, haqiqiy repo ichida bajariladigan kurslar. «Introduction to GitHub» bilan boshlang (20 daqiqa).
  2. Learn Git Branching — learngitbranching.js.org. Branch va merge'ni o'yin sifatida mustahkamlaydi. Bizda o'tilmagan rebaseni ham shu yerda ko'rasiz.
  3. Real loyihaga hissa qo'shing. Yoqqan o'zbekcha yoki open-source loyihani toping, kichik narsani tuzating (imlo xatosi ham bo'ladi!) va PR oching. Birinchi PR'ingiz — eng katta qadam.
    Buning yo'li alohida darsda: Dars 16 — Fork va open source ✅
🤝 Jamoaga qo'shiling — bilim shu yerda mahoratga aylanadi

Savol berish va boshqalarning muammosini o'qish — o'rganishning eng tez yo'li. Tanlang:

  • Stack Overflow — git tegi: aniq xato bo'yicha javob izlash uchun (avval qidiring — ehtimol javob bor).
  • r/git: workflow maslahati, «shunday qilsam to'g'rimi?» degan savollar uchun.
  • Uzbek Coders va o'zbek dev Telegram guruhlari: o'zbekcha so'rash uchun.

Boshlash uchun oson yo'l: shu kursda tushunmagan bir narsangizni tanlang va o'sha jamoada so'rang. Birinchi savol eng qiyini.

Kursdan tashqarida qolgan mavzular

Bular keyingi bosqich — poydevoringiz mustahkam bo'lgani uchun endi ularni o'zingiz ham o'zlashtira olasiz:

  • git stash — yarim ishni vaqtincha yig'ib qo'yish. Juda foydali, shuning uchun dars sifatida qo'shildi ✅;
  • git rebase — tarixni tekislash (kuchli, lekin ehtiyot talab qiladi);
  • git reflog — «hammasini yo'qotdim» degan holatdagi qutqaruv kamari;
  • GitHub Actions — testlarni avtomatik ishga tushirish (CI/CD).
Men shu yerdaman

Kurs tugadi, lekin men tugamadim. Ishda biror Git holatiga duch kelsangiz — xato, g'alati chiqish, «bu jamoada nega bunday qilinadi?» degan savol — bemalol yozing. Kerak bo'lsa yangi dars ham qo'shamiz: stash, rebase yoki ish joyingizdagi tartib bo'yicha.
