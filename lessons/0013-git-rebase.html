DARS 13 · QO'SHIMCHA · KURSDAN KEYIN

git rebase: tarixni to'g'ri chiziqqa keltirish

Bu darsdan keyin siz rebase nima qilishini aniq tushunasiz, uni xavfsiz ishlatasiz — va eng muhimi, uni qachon ishlatmaslik kerakligini bilasiz.

📱 O'qish ≈ 10 daqiqa 💻 Amaliyot ≈ 16 daqiqa Kerak: Dars 10, 08

Bu — kursdagi eng ehtiyot talab qiladigan mavzu

rebase tarixni o'zgartiradi. To'g'ri ishlatilsa — chiroyli, noto'g'ri ishlatilsa — jamoangizga muammo keltiradi. Shuning uchun bu darsda buyruqdan ko'ra qoida muhimroq. Qoidani yodlab olsangiz, qolgani oson.

Muammo: 10-darsdagi merge commitlar

10-darsda branch eskirganda git merge main --no-edit qilgan edik. U ishladi, lekin har safar merge commit qoldirdi. Uzoq loyihada tarix shunday ko'rinadi:

git log --oneline --graph * 9a8b7c6 Merge branch 'main' into login |\ | * 5d4e3f2 Hamkasb ishi * | 1a2b3c4 Mening ishim |/ * 7f6e5d4 Merge branch 'main' into login |\

Har kuni merge main qilsangiz — har kuni bitta merge commit. Ular hech qanday ish qilmaydi, faqat «shu kuni yangiladim» deb turadi. Ba'zi jamoalar buni shovqin deb hisoblaydi va tarix to'g'ri chiziq bo'lishini xohlaydi.

rebase nima qiladi

Sodda qilib: sizning commitlaringizni «ko'tarib olib», eng yangi mainning ustiga qayta qo'yadi.1 Go'yo siz ishni boshidanoq yangi main ustida yozgandek bo'lasiz.

Oldin — yo'llar ajralgan (7-darsdagi tanish holat):

Sizning c4 commitingiz eski poydevorda (c2) turibdi.

Keyin — git rebase main dan so'ng:

Tarix — to'g'ri chiziq. Merge commit yo'q. Lekin c4 yo'qoldi va o'rniga yangi c4′ paydo bo'ldi.

Eng muhim texnik haqiqat

rebase commitlarni ko'chirmaydi — u yangi commitlar yaratadi. Ichidagi o'zgarish bir xil, lekin hash boshqa (4c7788c → 8d72cdc). Eskilari tashlab yuboriladi.

Mana shuning uchun bu «tarixni qayta yozish» deb ataladi — va mana shuning uchun quyidagi qoida bor.

🔴 Oltin qoida — bittasi, lekin qat'iy

Rebase'ning oltin qoidasi

Push qilingan — ya'ni boshqalar ko'rgan — commitlarni hech qachon rebase qilmang.2

Nega? Rebase yangi commitlar yaratadi. Agar eskilari allaqachon GitHub'da bo'lsa va hamkasbingiz ularni olgan bo'lsa:

  • Sizda — yangi commitlar (yangi hash);
  • Unda — eski commitlar;
  • Git ikkalasini butunlay boshqa tarix deb ko'radi.

Push qilmoqchi bo'lsangiz, Git rad etadi (! [rejected]) va «--force qil» degan maslahat topasiz. --force esa hamkasbingizning ishini o'chirib yuborishi mumkin. Shuning uchun:

Boshlovchi uchun xavfsiz shakl

Faqat o'zingizning, hali push qilinmagan branch'ingizni rebase qiling.

Shubhangiz bo'lsa — merge ishlating. U har doim xavfsiz (7-dars). Merge bilan hech kim jarohatlanmagan.

merge yoki rebase?

Ikkalasi ham bir xil natija beradi — fayllaringiz oxirida bir xil bo'ladi. Farq faqat tarixning ko'rinishida:

mergerebase
Tarix Ajralish saqlanadi — rostgo'y To'g'ri chiziq — toza
Commitlar O'zgarmaydi Yangidan yaratiladi (hash o'zgaradi)
Xavfsizlik ✓ Har doim xavfsiz ⚠️ Push qilingan bo'lsa — xavfli
Qachon Shubha bo'lsa — shu O'z, hali push qilinmagan branch'da
Jamoalar turlicha qaror qiladi

Ba'zi jamoalar faqat merge ishlatadi, ba'zilari rebase talab qiladi. Ikkalasi ham to'g'ri — bu did masalasi. Ish joyingizga borganingizda «bu yerda qaysi tartib?» deb so'rang va o'shanga moslashing.

Rebase paytida konflikt

Konflikt bo'lishi mumkin — 8-darsdagi kabi. Lekin uch farq bor.

1. Boshqa buyruqlar

BuyruqNima qiladi
git rebase --abort Qochish yo'li. Rebase boshlangunga qadar bo'lgan holatga qaytaradi. ✓ Xavfsiz. Chalkashsangiz — birinchi shuni eslang.
git rebase --continue Konfliktni hal qilib git add qilgandan keyin — davom ettiradi. Merge'dagi git commitning o'rnida.
git rebase --skip Shu commitni butunlay tashlab ketadi. Kamdan-kam kerak — ishonchingiz komil bo'lmasa ishlatmang.

2. ⚠️ Belgilar TESKARI bo'ladi

Bu — eng chalkash joy, shuning uchun alohida ta'kidlayman.

Merge'da HEAD = siz turgan branch edi. Rebase'da esa Git commitlaringizni main ustiga bitta-bitta qo'yib chiqadi — shuning uchun o'sha payt «asos» bo'lib main turadi:

salom.txt — REBASE paytidagi konflikt
<<<<<<< HEAD
Salom, dunyo!main'niki
=======
Assalomu alaykum!SIZNIKI
>>>>>>> b353b15 (Branch: uzun salom)

Ya'ni yuqoridagi — main'niki, pastdagi — sizniki. Merge'dagining aksi. Adashmaslik uchun oson yo'l: pastdagi qatorda commit izohingiz yozilgan bo'ladi — o'shanga qarang.

3. Har commit uchun alohida

Branch'ingizda 3 ta commit bo'lsa, konflikt uch marta chiqishi mumkin — har biri uchun alohida hal qilib, har safar --continue deysiz. Terminalda Rebasing (2/3) kabi yozuv qayerdaligingizni ko'rsatib turadi.

git pull --rebase — 10-darsdagi sozlama shu edi

10-darsda bir martalik sozlama qilgandik:

git config --global pull.rebase false

Endi u nimani anglatishini tushunasiz: «pull qilganda, ajralish bo'lsa merge ishlat» degan edik. Muqobili — true, ya'ni rebase.

Bir martalik sinab ko'rish uchun sozlamani o'zgartirish shart emas:

git pull --rebase

Bu xavfsiz, chunki u faqat sizning mahalliy, hali push qilinmagan commitlaringizni qayta joylashtiradi. Ko'p jamoalar aynan shuni tavsiya qiladi.

Amaliyot: rebase'ni xavfsiz muhitda sinab ko'ramiz

Mashq nusxa papkada (~/Projects/Learn/Git-nusxa) va push yo'q — ya'ni oltin qoidani buzmaymiz.

Tahrirlagich haqida

git rebase --continue odatda commit izohini tasdiqlash uchun matn tahrirlagichini ochadi. Mashqda chalkashmaslik uchun buyruq oldiga GIT_EDITOR=true qo'shamiz — bu «tahrirlagich ochilmasin, izoh o'z holicha qolsin» degani.

Haqiqiy ishda tahrirlagich ochilsa: Ctrl+X (nano) yoki Esc keyin :wq (vim). Bir martalik yechim: git config --global core.editor nano.

A qism — oddiy rebase

  1. Tayyorgarlik

    Toza boshlanish nuqtasi yaratamiz.

    cd ~/Projects/Learn/Git-nusxa && git switch main && echo "Baza" > rb-baza.txt && git add rb-baza.txt && git commit -m "Rebase mashqi: baza"

    Kutilgan natija: 1 file changed.

  2. Branch ochib, «o'z ishingizni» qiling

    git switch -c mening-ishim && echo "Mening ishim." > meniki.txt && git add meniki.txt && git commit -m "Mening ishim qo'shildi"

    Kutilgan natija: yangi branch va commit.

  3. Commitingizning hash'ini yozib oling

    Bu muhim — rebase'dan keyin taqqoslaymiz.

    git log --oneline -1 4c7788c Mening ishim qo'shildi

    Kutilgan natija: 7 belgili hash. Uni eslab qoling (sizda boshqacha bo'ladi).

  4. «Hamkasbingiz» mainga ish qo'shsin

    Bu ajralishni yaratadi.

    git switch main && echo "Hamkasb ishi." > rb-hamkasb.txt && git add rb-hamkasb.txt && git commit -m "Hamkasb ishi qo'shildi"

    Kutilgan natija: commit yaratildi.

  5. Ajralishni ko'ring

    git log --oneline --graph --all -4 * 9876e39 Hamkasb ishi qo'shildi | * 4c7788c Mening ishim qo'shildi |/ * eadb7cb Rebase mashqi: baza

    Kutilgan natija: |/ belgisi — ikki yo'l ajralgan. Rasmdagi «oldin» holati.

  6. 🔑 Rebase qiling

    O'z branch'ingizda turib. Yo'nalish merge'dagidek: kimning ustiga qo'ymoqchi bo'lsangiz — o'shani yozasiz.

    git switch mening-ishim && git rebase main Successfully rebased and updated refs/heads/mening-ishim.

    Kutilgan natija: «Successfully rebased». 1-g'alaba. 🎉

  7. Natijani ko'ring — ikki narsaga e'tibor bering

    git log --oneline --graph --all -4 * 8d72cdc Mening ishim qo'shildi * 9876e39 Hamkasb ishi qo'shildi * eadb7cb Rebase mashqi: baza

    Kutilgan natija: ikkita muhim o'zgarish —
    1. |/ yo'q: tarix to'g'ri chiziq;
    2. commitingiz hash'i o'zgargan (4c7788c → 8d72cdc) — bu yangi commit. 2-g'alaba. 🎉

B qism — konfliktli rebase

  1. Konflikt uchun holat yarating

    Bitta faylning bitta qatorini ikki tomondan o'zgartiramiz (8-darsdagi retsept).

    git switch main && echo "Salom!" > rb-salom.txt && git add rb-salom.txt && git commit -m "Salom fayli"

    Kutilgan natija: commit yaratildi.

  2. Branch'da o'zgartiring

    git switch -c konflikt-branch && echo "Assalomu alaykum!" > rb-salom.txt && git commit -am "Branch: uzun salom"

    Kutilgan natija: yangi branch va commit.

  3. mainda o'sha qatorni boshqacha o'zgartiring

    git switch main && echo "Salom, dunyo!" > rb-salom.txt && git commit -am "Main: dunyo qo'shildi"

    Kutilgan natija: commit. Endi konflikt muqarrar.

  4. 💥 Rebase qiling

    git switch konflikt-branch && git rebase main CONFLICT (content): Merge conflict in rb-salom.txt error: could not apply b353b15... Branch: uzun salom hint: Resolve all conflicts manually, mark them as resolved with hint: "git add/rm <conflicted_files>", then run "git rebase --continue".

    Kutilgan natija: CONFLICT va Git'ning aniq maslahati. E'tibor bering: git commit emas, git rebase --continue deyilgan.

  5. Belgilarni ko'ring — teskari ekaniga ishonch hosil qiling

    Darsning eng chalkash joyi — o'z ko'zingiz bilan ko'ring.

    cat rb-salom.txt <<<<<<< HEAD Salom, dunyo! ======= Assalomu alaykum! >>>>>>> b353b15 (Branch: uzun salom)

    Kutilgan natija: yuqorida mainniki («Salom, dunyo!»), pastda sizniki («Assalomu alaykum!») — va pastki qatorda sizning commit izohingiz turibdi. Merge'dagining aksi.

  6. Avval qochish yo'lini sinab ko'ring

    Ishonch uchun: chalkashsangiz orqaga qaytish mumkin.

    git rebase --abort && git status --short

    Kutilgan natija: hech narsa chiqmaydi — toza. cat rb-salom.txt deng: belgilar yo'q, faqat sizning variantingiz. 3-g'alaba. 🎉

  7. Qayta rebase qilib, bu safar hal qiling

    git rebase main # konflikt chiqadi, keyin yakuniy matnni yozamiz: echo "Assalomu alaykum, aziz dunyo!" > rb-salom.txt

    Kutilgan natija: fayl tayyor — belgilarsiz, siz tanlagan matn bilan.

  8. «Hal qildim» deb belgilang va davom ettiring

    git add — 8-darsdagi kabi. Keyin commit emas, rebase --continue.

    git add rb-salom.txt && GIT_EDITOR=true git rebase --continue Successfully rebased and updated refs/heads/konflikt-branch.

    Kutilgan natija: «Successfully rebased». 4-g'alaba — konfliktli rebase'ni yakunladingiz! 🎉🎉

  9. Yakuniy tarixni ko'ring

    git log --oneline --graph -4 && cat rb-salom.txt * 5f80e20 Branch: uzun salom * 07a35ba Main: dunyo qo'shildi * f63076d Salom fayli Assalomu alaykum, aziz dunyo!

    Kutilgan natija: to'g'ri chiziq — |\ yoki |/ yo'q — va faylda siz yozgan matn.

Diqqat: bu branch'larni push qilmang

Mashq nusxa papkada va push qilinmadi — ya'ni oltin qoida buzilmadi. Nusxa papkani tartibga solish kerak bo'lsa — ayting.

Yodda tuting (checklist)

💻 Amaliy qism kompyuterda

Amaliyotda avval oddiy rebase qilasiz va ikki narsani ko'rasiz: tarix to'g'ri chiziqqa aylanadi va commitingiz hash'i o'zgaradi. Keyin ataylab konflikt yasab, belgilar teskari ekanini o'z ko'zingiz bilan ko'rasiz, --abort bilan chekinasiz, so'ng hal qilib --continue bilan yakunlaysiz. 16 qadam, hammasi nusxa papkada va push'siz.

Tekshirib ko'ramiz (quiz)

SAVOL 1 Rebase commitlaringizga nima qiladi?

To'g'ri. Ichidagi o'zgarish bir xil, lekin bu boshqa commitlar. Aynan shuning uchun oltin qoida bor.

SAVOL 2 Rebase'ning oltin qoidasi nima?

To'g'ri. Ular boshqalarda ham bor — siz yangi tarix yaratsangiz, ikkalasi mos kelmaydi va --force kerak bo'lib qoladi. Bu esa hamkasbingizning ishini o'chirishi mumkin.

SAVOL 3 Rebase paytida konfliktda <<<<<<< HEAD ostidagi matn kimniki?

To'g'ri, va bu chalkashtiradigan joy. Rebase Git commitlaringizni main ustiga qo'yib chiqadi — shuning uchun «asos» main bo'ladi. Pastki qatorda sizning commit izohingiz yoziladi.

SAVOL 4 Konfliktni hal qildingiz va git add qildingiz. Keyin?

To'g'ri. Rebase davom etayotgan jarayon — uni --continue bilan davom ettirasiz. Git buni terminalda ham aytib turadi.

Eslab ayting (o'zingizni sinang)

Avval o'zingiz javob bering, keyin ochib tekshiring.

Rebase bir jumlada nima qiladi?

Commitlaringizni «ko'tarib olib», eng yangi mainning ustiga qayta qo'yadi — natijada tarix to'g'ri chiziq bo'ladi.

Oltin qoida — va nega?

Push qilingan commitlarni rebase qilmang. Chunki rebase yangi commitlar yaratadi; eskilari hamkasblaringizda qoladi va ikki tarix mos kelmaydi.

Shubhangiz bo'lsa — merge yoki rebase?

Merge. U har doim xavfsiz. Rebase faqat o'z, hali push qilinmagan branch'ingiz uchun.

Rebase konfliktida belgilar qanday joylashadi?

Teskari (merge'ga nisbatan): yuqorida HEAD = mainniki, pastda — sizniki. Pastki qatorda sizning commit izohingiz yozilgan bo'ladi.

Rebase'dagi uchta buyruq?

--abort (orqaga qayt) · --continue (hal qilgandan keyin davom et) · --skip (bu commitni tashlab ket — kamdan-kam).

↩︎ Takrorlash: merge'da HEAD kimniki edi?

Siz turgan branchniki. (Dars 08) — rebase'da esa aksi.

Cho'ntak xulosasi
  • Rebase = commitlaringizni yangi main ustiga qayta qo'yish. Tarix to'g'ri chiziq bo'ladi.
  • ⚠️ U commitlarni ko'chirmaydi — yangisini yaratadi (hash o'zgaradi).
  • 🔴 Oltin qoida: push qilingan commitlarni hech qachon rebase qilmang.
  • Shubha bo'lsa — merge. U har doim xavfsiz.
  • O'z branch'ingizda: git rebase main.
  • Konfliktda: belgilar teskari (yuqorida main, pastda siznikingiz).
  • Hal qilish: tahrirla → git add → git rebase --continue.
  • Qochish yo'li: git rebase --abort.
  • git pull --rebase — xavfsiz, chunki faqat mahalliy commitlaringizga tegadi.
